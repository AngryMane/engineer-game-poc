# 共通システムと障害案件の設計（設計者向け・解答を含む）

## 方針

- 問題ごとに新しいグラフを作らず、共通システム1つの上に複数の障害案件を置く。各案件は正常なシステムにその案件の故障1件だけを入れて始まる。修復状態は案件間で引き継がない。
- システムは既存8問の故障の仕組みをすべて受け持てる機能だけで構成する。どのノードもいずれかのシステム出力に寄与し、子が1つだけのモジュールは作らない（テストで検証）。
- 全案件に障害レポートを付ける。レポートは症状と観測値だけを示し、原因を名指ししない。値は隠した操作記録を故障ありのシステムで再生して求めるため、記述と実際の挙動がずれない。
- 出力条件と公開検証ケースは全案件で共通。修復判定はシステム全体の出力条件だけで行い、代替修復も受け入れる。

## 共通システム（30ノード・3階層・10出力）

| モジュール | ノード | 役割 |
|---|---|---|
| System | N01〜N06（入力）、N21〜N30（出力） | 供給・要求・準備・取り込み・使用の5入力、外部消費、10出力 |
| Intake | N07 | 供給量を周期的に取り込む |
| Load | N08, N09 | 周期負荷（周期12・幅3・大きさ2） |
| Reference | N10, N11 | 使用量の換算係数（1）と出力単位の倍率（2）。問い合わせで応答 |
| Preparation / Accounting | N12 | 要求 × 換算係数 = 使用量 |
| Preparation / Balance | N13 | 余力 = 供給 − 使用量 − 周期負荷 − 外部消費 |
| Preparation / Storage | N14, N15 | 準備量の蓄積（上限24）と準備完了 |
| Conversion | N16, N17 | 供給と要求を出力単位に換算（変換値は上限30） |
| Setting / Control, Holding, Consumption | N18, N19, N20 | 設定値の受理・保持・使用 |

出力：N21 変換値、N22 余力、N23 準備量、N24 準備完了、N25 周期負荷、N26 要求の換算値、N27 受理した設定値、N28 使用結果、N29 供給量の確認、N30 外部値の確認。

時間規則：手動入力は反映から2ステップ後にtimer計算へ届き、timer段ごとに1、出力への配送で1を加える。

## 案件と解答

| 案件 | 故障 | 直接修復 | 主な手掛かり |
|---|---|---|---|
| 00 | なし | — | 経路の段数で反映時刻が違う |
| 01 | N09.load 2→8 | N09.load=2 | 下がる時刻がN25と一致。準備量は負荷を引かないため正常 |
| 02 | N14.rate 1→0.25 | N14.rate=1 | 余力は正常。準備量の増分だけが小さい |
| 03 | N11.scale 2→3 | N11.scale=2 | N21とN26が同じ倍率でずれる。N29は正常 |
| 04 | N16.ceiling 30→20 | N16.ceiling=30 | 供給10以下では正常。N21が外部値によらず20で一定 |
| 05 | N07.interval 1→4 | N07.interval=1 | 変更時刻によって遅れが変わる。N29は遅れない |
| 06 | N10.factor 1→2 | N10.factor=1 | 要求0で消え、要求に比例して余力不足と準備の遅れが大きくなる。N26は別の倍率で正常 |
| 07 | N19.retention 1→0 | N19.retention=1、またはN20.useAck=1 | 取り込み後、使用せずに解除すると保持値が消える |

03と06は別々の参照値を使うため、片方を解いても他方は自明にならない。01と02、02と06はどの出力が正常かで切り分けられる。

## 検証

`src/cases/cases.test.tsx`で、全案件が同じグラフ・階層・出力条件を使うこと、余計なノードやモジュールがないこと、正常なシステムが全検証ケースを通ること、各故障が失敗し、直接修復と代替修復で通り、近道の補正では通らないこと、各案件のレポートが正常時と異なる観測を含むこと、画面に内部ノードIDが出ないことを確認する。
