# 時間操作と実験再生の設計

開発者向けのステップデバッガのような時間操作をやめ、条件を変えた実験と観測で再現条件を見つけるゲームに寄せるための改修です。エンジンの離散tick・イベント駆動の仕組みと `step()` はそのまま残し、プレイヤー画面から逐次実行ボタンだけを外しています。

## 画面の時間操作

| 操作 | 動作 |
|---|---|
| Run | 表示速度に合わせて 1 tick ずつ進める。速度は 1x（480ms/tick）・4x・8x |
| Pause | 時間の進行だけを止める。キュー・状態は変わらない。停止中も仕様・履歴の閲覧、ノート、実験の編集ができる |
| Reset | シナリオ初期状態に戻す（既存の規則どおり）。記録はここから始まる |
| Restart | 設定と手動編集した状態値を保ち t=0 から再実行（既存の規則どおり）。記録はここから始まる |

`+1`・`+12`・`+36` ボタンは、階層画面（`HierarchyPlay`）とテスト用の旧フラット画面（`FlatApp`）の両方から外しました。表示速度は表示のペースだけを変え、1回のタイマー呼び出しで進むのは常に1 tickです（`src/useTicker.ts`）。タイマーは常に1つで、Pause や速度変更では新しいタイマーを作る前に古いものを止めます。Pause を押した瞬間にフラグも下ろすので、React の反映前にタイマーが発火しても世界は進みません。

## 操作シーケンス（`src/experiment.ts`）

```ts
type Operation =
  | {atTick; kind:'setInput';  target; value}
  | {atTick; kind:'intervene'; target; value; purpose:'experiment'|'repair'}
  | {atTick; kind:'request';   target};
```

- **時刻の定義**: `atTick: t` の操作は、画面に `t` が表示されている間に適用されます。つまり tick t の処理が終わったあと、tick t+1 の処理の前です。プレイヤーが停止中に `t` で入力を変えるのと同じです。
- **同じtickの順序**: 配列の順番（登録順）で適用します。記録時はクリック順、編集時は表の上から順です。編集後は tick で安定ソートするので、同じ tick の中の順番は保たれます。
- **API**: 各操作は `setInput` / `intervene` / `requestNode` を通して適用します。値の範囲・刻み、編集できる設定かどうか、外乱INPUTの編集禁止は、通常の操作と同じ検証を通ります。
- **無効な操作**: 再生開始前にシーケンス全体を検証し（`validateSequence`）、無効なら再生しません（World は初期状態のまま、状態は `failed`）。実行中にエンジンが例外を出した場合は、その tick の操作をすべて取り消して止めます。
- **決定論**: 再生は描画やタイマーに依存しない純粋関数です（`advancePlayback`）。1 tick ずつ進めても、8 tick ずつ進めても、最後まで一気に進めても結果は同じです（テストで確認）。

## 実験と初期条件

`Experiment` は次を持ちます。

- `setup`: シナリオID、外乱のシード（表示用）、開始時の World スナップショット全体。スナップショットには状態・設定・配送待ちキュー・外乱の乱数状態が含まれるため、途中の時刻から始めた記録も同じ結果になります。
- `operations`, `until`: 操作シーケンスと終了tick。
- `name`, `prediction`（事前予測）, `memo`（結果メモ）: プレイヤーが書くもの。結果とは分けて保存します。
- `outcome`: 再生して計算した結果です。時系列、出力ログ、出力ごとの異常発生・回復時刻、終了時に条件を満たしていない出力、完了か失敗かを持ちます。
- `parentId`, `origin`: 変種の場合は元の実験。元の実験は変更しません。

記録は Reset・Restart・「ここから記録し直す」の時点から自動で始まり、プレイヤーの入力・編集・問い合わせを、そのとき画面に出ていた tick で記録します。「実験として保存」で現在の記録を実験にします。

## 現在のセッションと再生の分離

実験の再生は、現在のセッションとは別の World で行います。再生中は画面が再生中の World を表示し、ツールバーに「実験を再生中」、再生状況の欄に現在時刻・次の予定操作・完了／失敗を表示します。再生中は直接の操作を受け付けません（変えたい場合は変種を作ります）。「セッションに戻る」で、再生前のセッションをそのまま表示します。そのため、修復済みのセッションが再生で上書きされることはありません。クリア判定のモーダルは、セッションの World に対してだけ出ます。

## 保存形式

- 保存キーは `causal-hierarchy-session-v15`、形式は `version: 15` です。`recording`（開始スナップショットと操作列）、`experiments: Experiment[]`、レポート別のヒント開示数 `reportHints`、表示速度 `speed` を追加しました。
- **v14 からの移行**: v15 の保存がなければ、旧キー `causal-hierarchy-session-v14` を読んで変換します。旧データは書き換えず、消しません。`runStart`/`runActions` は `recording` に変換します。レシピのある実験は `origin:'migrated'` の実験に変換し、結果は再生して計算し直します。v14 の `notes` は `memo` に移ります。
- **非互換**: v14 の旧案件 `case-01`〜`case-07` の保存は、画面から選べるページがなくなったため読み込めません（単独故障の案件は統合ページに置き換えました）。練習（`case-00`）の保存は読み込めます。

## 障害レポートのページ統合

同じグラフに対するレポートは1ページにまとめました。障害対応ページ（`incidentScenario`）は、共通システムに案件01〜07の故障をすべて同時に入れた状態で始まります。7件のレポートを一覧で表示し、ヒントはレポートごとに開きます。各レポートは、元の案件の隠れた操作記録を同時故障のシステムで再生した値を表示します。単独故障では正しかった「準備は正常」などの記述は、同時故障では成り立たないため、観測した事実だけを書く文面に直しました。7件すべてを修復すると全検証ケースを満たします（07はN20.useAckでの代替修復も受け付けます）。修復が1件でも欠けると不合格です（テストで確認）。

## ゲームデザイン上の評価（未検証）

- **改善仮説**: 逐次ステップ追跡ができなくなる一方で、操作時刻を1つだけ変えた変種を並べて比べられるようになります。これにより、ノードを追跡するより先に「いつ・どの順で操作すると症状が出るか」という仮説を立てやすくなります。とくに案件05（変更時刻で遅れが変わる）と07（解除と使用の順番）で効くと考えています。
- **悪化リスク**:
  - 実験を保存するまで比較できないため、手間が増えます。
  - 1x では短い現象を見逃すことがあります。この場合は Pause して Timeline と Output log で確認します。
  - 原因の見当がつかないまま変種の数だけが増えるおそれがあります。
  - 7件同時故障では、単独案件で用意していた「この出力は正常なので切り分けられる」という手掛かりが弱まり、難易度が大きく上がります。
- **検証方法**: 旧UI（PR #1 時点）と新UIで同じシナリオを遊んでもらい、比べます。見る項目は、仮説の発話、実験・操作の回数、再現条件を見つけたかどうか、原因の説明、主観的な洞察感です。初見プレイヤーでの検証はまだしていません。
- **残る課題**:
  - 実験の削除と並べ替えがありません。
  - 変種に追加できるのは通常入力だけで、内部設定の編集は記録からしか入りません。追加用の選択肢に非公開ノードの名前を出さないためです。
  - 実験の比較表は全実験を1表に並べるだけで、2件の差分を強調する表示はありません。
  - 外乱シードを変えた変種は作れません。
