# 同型船の不具合調査：設計メモ（ネタバレを含む・実装前）

2026-10-19 に合意した方向をまとめたものです。数値はすべて仮の値で、実装の前にシミュレーションで確かめて調整します。

## 1. 設定

- プレイヤーは、造船会社の**不具合調査メカニック**です。
- 自社の同型船「カナリア級」で、不具合の報告が相次いでいます。何隻かは爆発四散しました。乗員は全員、脱出ポッドで無事でした。
- 会社は在庫の同型船を**試験航海**に出して、不具合を再現させます。
  - 雇われたクルーが、メカニックの書いた**指示書**どおりに操作卓を操作します。
  - メカニックも毎回その船に乗り込み、部屋を移動しながら表示を見て、整備区画の設備を点検します。
- 再現できれば、船は爆発します。爆発の前に、クルーとメカニックは脱出ポッドで逃げ、クルーは文句を言います。
- 直せれば、何事もなく帰港します。クルーは退屈そうにしています。
- 在庫船の数に上限は付けません。「本日の爆発：12 隻」のような集計を、笑いとして表示するだけです。

トーンは漫画的にします。誰も死なず、些細な原因で船が派手に壊れることを笑えるようにします。

## 2. 用語（「用語：クルーとメカニック」の更新）

| 用語 | 意味 |
|---|---|
| クルー | 試験航海に雇われた乗員。役割（科学・生命維持・電力・熱制御）ごとに自分の部屋を持つ。指示書どおり自分の部屋の操作卓を操作し、自分の部屋の表示を見る。inner ノードには操作も参照もできない |
| メカニック | プレイヤー。毎回試験航海に乗り込む。船外以外のすべての部屋に入れる。inner ノードを点検し、設定を変えられる |
| 試験航海 | 今の「実験」。在庫船1隻を同じ初期状態から出して、指示書どおりに操作する |
| 指示書 | 今の「操作シーケンス」。どの tick に、どの部屋の操作卓で、何をするか |
| 指示書の書き換え | 今の「変種」。元の指示書は残る |
| 航海記録 | 今の「実験の結果」。表示の時系列、警報、爆発した時刻と原因 |
| 不具合報告 | 今の「障害レポート」。実際に不具合が起きた船のクルーが、自分の部屋で見たことだけを書く |
| 航路 | 外乱（放熱ループ温度の揺らぎ）のシード。同じ航路なら同じ揺らぎになる |

- これで、Run / Pause を除いた実験の道具はすべて物語の中の道具になります。Run / Pause / 速度は、引き続き物語の外の道具です。
- 修理は、メカニックが試験航海中の船の設定を変えることです。運用契約をすべて満たし、かつ爆発しなければ、改修通知を発行してクリアになります。

## 3. 爆発に至る共通の仕組み（新規）

爆発は唐突に起こさず、一段ずつ悪化するのを見せてから起こします。どの段も、どこかの部屋の表示か、設備パネルで見えるようにします。

| 段 | 仕組み（仮の値） | どこで見えるか |
|---|---|---|
| 熱暴走 | 機器ラック温度が 42 °C を超えた状態が 3 tick 続くと、電子機器が発火する | 熱管理室（独立監視の温度）、機器ベイのラック |
| 酸素の滞留 | O₂タンクが満杯になると、逃がし弁が機器ベイへ酸素を放出する（コスト削減のための仕様）。換気ファンが船外へ排出する | 機器ベイの新しい設備「換気ファン」「機器ベイ酸素濃度」 |
| 火花 | ペイロードが実験運転を始めるとき、起動電流で火花が出る | 科学ラボ（ペイロード状態の切り替わり） |
| 火災 | 機器ベイの酸素濃度が 30 % 以上のときに火花か熱暴走が起きると、火災になる。熱暴走は、酸素濃度に関係なく火災になる | 全部屋に警報 |
| 爆発 | 火災が 5 tick 続くと、船が爆発する。その時点で試験航海の記録を止める | 全画面の演出 |

- 爆発したら、その試験航海はその tick で終わります。航海記録には、「何 tick で爆発」と「火災の原因（熱暴走か火花か）」を残します。
- 比較表には爆発の時刻が並ぶので、どの指示書で壊れたかがひと目でわかります。
- 正常な船は、どの公開検証ケースでも火災にならないようにします。熱暴走のしきい値と、ファンの排出量に余裕を持たせます。

## 4. 不具合（複数）

同じ製造ロットの在庫船には、**3つの不具合が同時に入っています**。報告はそれぞれ別の船・別の日から来ます。

各不具合は、別々の操作条件でだけ表に出るように設計します。そうすれば、試験航海で1つずつ切り分けられます。1つ直すと、同じ指示書でも別の原因で爆発したり、爆発が遅れたりします。この「直したのに、まだ爆発する。でも今度は時刻が違う」も、発見の一つとして使います。

### 不具合A：冷却ポンプの負荷区分（既存の案件を拡張）

| 項目 | 内容 |
|---|---|
| 故障 | 配電盤で、冷却ポンプが重要負荷ではなく一般負荷になっている |
| 再現条件 | 実験運転を始めた数 tick 後に O₂ 増産を始める。増産が遅ければ起きない |
| 連鎖 | O₂ 増産が先に主バスを確保する → ポンプ給電許可が頭打ちになる → 冷却液流量が不足する → ラック温度が 42 °C を超える → 熱暴走 → 火災 → 爆発（実験開始から約 40 tick 後） |
| 手掛かり | 熱管理室の冷却液流量が正常な日の半分程度。ポンプは「運転中」のまま。電力管理室では主バス負荷が定格付近 |
| 直接の修理 | 負荷区分を重要負荷に戻す。今の代替修理（増産の要求電力を下げる、最低流量を上げる）も認める |

### 不具合B：換気ファンの排出量

| 項目 | 内容 |
|---|---|
| 故障 | 機器ベイの換気ファンの排出量が、仕様の 1.5 L/min ではなく 0.3 L/min になっている |
| 再現条件 | O₂ 増産を長く続けてタンクを満杯にしたあとで、実験運転を始める。順番が逆なら起きない。不具合Aとは逆の順番 |
| 連鎖 | 増産を続ける → タンクが満杯になる → 逃がし弁が機器ベイへ放出する → ファンが追いつかず、酸素濃度が上がる → 実験運転を始めた火花 → 火災 → 爆発（実験開始の直後） |
| 手掛かり | 生命維持室のタンク残量が 100 % のまま。爆発が実験開始の直後に起きる（不具合Aでは数十 tick 後）。機器ベイの酸素濃度の設備パネル |
| 直接の修理 | ファンの排出量を 1.5 に戻す。代替：逃がし弁の作動残量を 100 % より上にする設定があれば、それも可（要検討） |
| 帳尻合わせ（不合格） | 実験運転をしない。ペイロードを止めておく |

### 不具合C：温度センサーの校正

| 項目 | 内容 |
|---|---|
| 故障 | ラック温度センサーの校正オフセットが 0 ではなく −3 °C で、実際より低く報告する |
| 再現条件 | 暑い航路（放熱ループ温度が高めに揺らぐ航路）で、実験運転を長く続ける。涼しい航路では起きない |
| 連鎖 | センサーが低く報告する → 冷却制御が流量を上げきらない。ペイロードの熱保護も遅れる → 暑い航路ではラック温度が 42 °C を超える → 熱暴走 → 火災 → 爆発 |
| 手掛かり | 熱管理室の独立監視の温度と、設備パネルで見えるセンサーの報告値がずれている。航路によって結果が変わる |
| 直接の修理 | オフセットを 0 に戻す |
| 必要な新機能 | 指示書で航路を選べるようにする（今は外乱のシードを変えられない） |

### 3つが同時に入っていることの扱い

- 報告の日の指示書を、3つの不具合が入った在庫船で再生したとき、どれも**その報告の原因で最初に**火災になるように数値を調整します。報告の値は、今と同じく隠した指示書から再生して求めます。
- 不具合Aの日（実験 → 早い増産）では、タンクが満杯になる前に熱暴走が起きるようにします。
- 不具合Bの日（長い増産 → 実験）では、熱が上がる前に火花で火災になるようにします。Bだけ直すと、同じ日がAの熱暴走で遅れて爆発する可能性があります。これは発見として使えるので許容します。
- 不具合Cの日は、増産しない日にします。そうすれば、AとBが表に出ません。
- クリア条件は、3つとも直して、公開検証ケースのどれでも運用契約を守り、爆発しないことです。

## 5. 演出

| 場面 | 演出 |
|---|---|
| 悪化の途中 | 表示に警報が出る。各部屋のクルーの声（「ちょっと暑くない？」「タンクがずっと満タンなんだけど」）。ほかの部屋の警報は、部屋の名前だけを知らせる |
| 火災 | 全部屋に警報。部屋の色が変わる。クルーが騒ぐ |
| 爆発 | 配置図の船が壊れて飛び散る。脱出ポッドが飛び出す。クルーの文句（「だから言ったのに」）。航海記録に「t=48 爆発（機器ベイの熱暴走）」 |
| 修理後の確認 | 同じ指示書で試験航海を出すと、何事もなく帰港する。クルーは退屈そう。爆発していた時刻に「何も起きなかった」と表示して対比を見せる |
| 集計 | 「本日の爆発：n 隻」。上限なし |

演出は、因果の順番がわかるように出します。たとえば、爆発の直前に「流量不足 → 温度上昇 → 熱暴走」の順に、関係した部屋を光らせます。

## 6. 実装の順番（案）

1. 爆発に至る共通の仕組み（機器ベイ酸素濃度、換気ファン、火花、火災、爆発）をエンジンの上に作り、正常な船で爆発しないことをテストする。
2. 不具合A・B・Cを入れ、各報告の日が狙った原因で最初に爆発するよう数値を調整する。
3. 航路の選択を指示書に足す（不具合Cのため）。
4. 言葉を「試験航海」「指示書」「航海記録」などに置き換える。
5. 演出（警報、クルーの声、爆発、帰港、集計）を足す。

## 7. 未確認・要検討

- 不具合Bの代替修理を何にするか。
- 不具合Cの「暑い航路」を、プレイヤーにどう選ばせるか。航路名と、その航路の気温の目安を見せるかどうか。
- 3つ同時に入れたとき、報告の日ごとに原因を分けられるか。シミュレーションで確かめるまでは確定ではない。
- クルーの声の量。多すぎると、手掛かりがどこにあるのかわかりにくくなる。
